IDGraph3 · connectedComponents() · config comparison

MAX_FANOUT/STAR_THRESHOLD: 32/10 vs. 16/6

Two full connected-components runs on the same ~4.9B-node identity graph, differing only in how aggressively per-key grouping evidence is trusted. 32/10 is the looser config; 16/6 is far stricter.

Methodology, briefly

Nodes are (type, value) identifiers across six types (HARDWARE_IDFA, HARDWARE_ANDROID_AD_ID, HEM_MD5, ID5_UID, TTD, ST). Edges connect two nodes when they co-occur under a shared grouping key (individual_id5, individual_id_tapad, or liid). MAX_FANOUT caps how many distinct nodes a single grouping-key value is allowed to tie together before that key's evidence is discarded entirely — it is the actual trust/individual-vs-family lever. STAR_THRESHOLD only controls whether a surviving group is stored as a full pairwise clique (≤ threshold) or a cheaper hub-and-spoke star (above it) — a pure cost lever that does not change which nodes end up merged. Connected components are computed via GraphFrames; a node's component is the full transitive closure of everyone it's linked to, directly or indirectly. The giant component (a.k.a. "super cluster") is, in both configs, by far the largest single component — orders of magnitude bigger than the next-largest, with nothing in between.
A note on units. Every figure in this report is a NODES statistic unless flagged COMPONENTS — e.g. the giant component's size is how many nodes it contains, not a count of giant components (there is exactly one giant component in each config, by definition). The dedicated component-count distribution further down is the one section built the other way around.

Key findings

  • Tightening curbs the giant component, but non-linearly. Only two data points exist (32/10, 16/6) — the jump from 47.3% to 14.19% suggests a percolation-like threshold effect rather than a smooth response, but the shape in between (and below 16/6) is unknown.
  • The improvement isn't free. Singleton rate nearly doubled (25.01%→49.21%) — nearly half the graph is now fully isolated. This is a real precision/recall-style tradeoff, not a clean win.
  • TTD is the more stubborn contributor. Its share of the giant component rose under tightening (28.94%→35.85%) while hardware types fell (e.g. HARDWARE_IDFA 14.17%→8.35%) — hardware-driven bridging was cut far more effectively than TTD-driven bridging.
  • A specific pathology resolved. 32/10 showed near-total TTD dominance (79–81%) in the 257–1024 component-size range, breaking an otherwise smooth trend. At 16/6 this is completely gone — clean evidence MAX_FANOUT did targeted, not uniform, work.
  • "Connected excluding super cluster" rose for every type despite overall connected population dropping — tightening converts supercluster membership into smaller ordinary identities as much as it destroys connections outright.
  • ID5_UID is the most resilient type across every metric in both configs — highest pct_conn, smallest connectivity drop, dominant and growing share of the connected population.
  • The id5 n=16 anomaly recurs a third time (raw id5 histogram, 32/10 type-mix, 16/6 type-mix) — a single-point spike at exactly size 16 in an otherwise smooth curve, appearing whether or not 16 happens to be our own MAX_FANOUT boundary. Points at an artifact upstream in ID5's own data, not our pipeline.
  • Nodes and components tell opposite stories about where the graph's mass sits. At 16/6, size-2 components outnumber the giant component roughly 108 million to 1 — yet the single giant component still holds more than 3× as many nodes (697.2M vs. 216.8M). The graph is simultaneously "mostly small components" and "mostly giant-component nodes," depending which unit you count in.

Caveats

  • 32/10's per-type breakdowns (type-mix %, raw node counts by type, CDF) are reconstructed from the published histogram + type-mix percentages, not a direct query — verified within 0.01% of known exact type totals, but not bit-for-bit exact like the 16/6 figures. The overall (not-by-type) bucket totals and component counts, by contrast, are the real per-size histogram as directly measured — Σ(size × count) across all 573 distinct sizes plus the giant component reproduces both known totals (4,914,094,515 nodes, 1,478,773,504 components) exactly.
  • The id5 n=16 anomaly affects the size-16 row/bucket in both configs — treat it as a known data artifact, not a real signal.
  • size2_type_pair_breakdown_fn (exact size-2 pair-type measurement) has not been run for either config — the "~85% of size-2 pairs are ID5_UID↔ID5_UID" claim implied by the type-mix data is still indirect.
  • Edge-level views (type×type matrix, weight/via_type_count histograms) are intentionally out of scope for this report.
  • Exactly which of 32/10 or 16/6 is the "better" operating point depends on whether over-merging or under-merging is the more costly error for the intended use case — this report doesn't resolve that, only quantifies the tradeoff.
  • The "by number of components" distribution is now fully exact for both configs — each has a real, directly-measured per-size histogram (573 distinct ordinary sizes apiece). The 32/10 histogram came from an earlier dedicated component-size-distribution analysis; the 16/6 histogram was recovered from the raw Databricks output pasted during the session that produced this report's first draft, which had only been summarized (not preserved in full) before now.
